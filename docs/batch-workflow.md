# 今後の追加バッチ運用

## 既存問題を会話へ読み込まない

- `data/questions.jsonl` と `data/reviews.jsonl` を会話に全件貼り付けない。既存問題はローカル処理だけに使う。
- `python scripts/quiz_index.py check 051` のように、バッチ単位で正規化設問の衝突、source IDの衝突、重複回答の件数だけを調べる。詳細を開くのは衝突行だけにする。
- バッチ索引は `work/quiz-index.sqlite` に置く。Git管理しない。正本のSHA-256が変わった場合のみ自動更新する。
- 読み・分類・難易度・タグの審査は50〜100問ずつに分け、`data/imports/batch-NNN.jsonl` から未処理範囲を選ぶ。会話へ渡すのは今回の範囲と出典の該当箇所だけにする。
- 作業再開時はマニフェストの総数、次の未処理ID、完了・保留数、直近の監査結果だけを見る。前のバッチ本文を再確認しない。

## バッチを作る

1. 出典の利用条件、固定版、取得日、ファイルSHA-256、元IDを確定して保存する。URLがあるだけでは事実照合済みにしない。
2. 追加候補は新しい連番IDで登録する。問題文・答え・読み・解説・タグは既存の8列を保つ。代表答えの次の要素はひらがな読みとし、読みや略称を推測で正解にしない。
3. 生成直後は `candidate` にする。各問の出典箇所、全ての事実主張、回答範囲、正式名称・表記、ジャンルとサブジャンル、難易度、2タグをレビュー記録に残す。難易度1・2は多くの一般成人に知られた知識に限る。
4. 同じsource内と既存全体の重複・回答漏れ・人名やシリーズ名の余分な語を確認する。異なる言い方の重複は機械の一致判定で確定せず、候補だけを人が読む。
5. 確認済みの問だけ `verified` に進め、保留には理由と重複先を記録する。人による公開承認が済むまで出題用承認CSVには出さない。
6. 監査ファイルには変更ID、変更前後、根拠、出典版、集計、保留数を保存する。CSVは正本JSONLから生成し、CSVだけを編集しない。
7. `python -m unittest discover -s tests -v`、`python scripts/quiz.py validate`、`git diff --check` を実行し、差分件数と既存ID不変を確認する。区切りごとにコミット・プッシュした場合は、リモートSHAを必ず照合する。

問題本文の全件再読込は行わず、索引が示す衝突行とレビュー対象の小バッチだけを確認する。

## 表記ゆれと途中回答の確認

- `scripts/quiz.py` の判定は、登録済みの正式表記・読み・明示された別名だけを正規化して比較する。答えの先頭だけ、意味のない断片、未使用の名称を自動許容しない。
- 問題を途中で止めても答えられるようにする修正は、答えを短くするのではなく、問題文の前半へ答えを絞る意味のある識別語を加える。候補語は人手確認キューで確認し、採用した設問はレビュー記録の変更履歴へ理由を残す。
- `python scripts/audit_human_review.py --date YYYY-MM-DD` で、読みにくい問題、回答が短すぎる問題、答えの露出、同じ答えの重複、回答範囲の編集、未審査候補を優先度付きで抽出する。`high`から確認し、別名を登録するときは実際の使用例を根拠にする。
